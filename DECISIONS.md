# Family Ledger - нюансы и договорённости вне схемы


## 1. Бизнес-правила, которые обеспечивает код, а не БД


- **Баланс цели не хранится** - вычисляется как `SUM(amount_cents)` по
  `contributions` для конкретного `goal_id`. Это ядро ledger-модели.
- **Нельзя изъять больше, чем сам внёс** - перед вставкой изъятия (`amount_cents < 0`
  в `contributions`) нужно посчитать текущий баланс конкретного пользователя
  по конкретной цели и сравнить.
  - **Гонка (race condition):** два одновременных изъятия от одного человека
    могут оба пройти проверку баланса до того, как любое из них закоммитится,
    и вместе увести в минус. Нужна транзакция с блокировкой на уровне БД -
    не решено, как именно (`SELECT ... FOR UPDATE` или иной механизм) -
    предстоит продумать при реализации.
- **Группа не может существовать без участников** - создание группы и
  добавление создателя в `group_members` должны происходить в одной
  транзакции, иначе на миг может появиться группа без единого
  члена. Схема этого не гарантирует.
- **Сумма процентов в `goal_shares` по одной цели должна давать 100** -
  проверяется в коде при создании/изменении долей. Отдельно - при делении
  суммы цели по процентам возможен остаток из-за целочисленных копеек
  (например, три равные доли по 33.33%) - нужно явное правило, куда девать
  остаток копейки.
- **В `goal_shares` и `contributions` может участвовать только тот, кто
  состоит в группе этой цели** - внешние ключи гарантируют только то, что
  `user_id`/`goal_id` существуют, но не то, что пользователь - участник
  нужной группы. Проверка - на уровне кода.

## 2. отложенные возможности

- **Видимость целей внутри группы** (например, цель видна не всем
  участникам). Реализация - отдельная таблица-исключение вроде
  `goal_visibility (goal_id, user_id)`: отсутствие строк для цели = видна
  всем участникам группы (текущее поведение по умолчанию), наличие строк =
  видна только перечисленным. Не требует изменений в существующих таблицах.
  **Важно:** текущая логика показа целей неявно опирается на допущение «нет
  ограничений → видно всем» - когда будем добавлять эту фичу,
  *расширяеем* фильтр, а не переписываем его с нуля.
- **Полноценная повторяемая 2FA** (двухфакторная аутентификация на каждый
  вход, с возможностью включить/выключить в настройках). Потребует своего флага (`two_factor_enabled` и т.п.) и хранилища
  секрета/кодов - добавится позже как новые поля/таблицы, без переделки
  `users`.
- **Подтверждение email кодом при регистрации** Вместе с ней отложена вся очередь краевых случаев:
  TTL кода, лимит попыток ввода, лимит запросов нового кода, поведение при
  уже занятой почте (риск enumeration attack - раскрытия факта существования
  аккаунта через слишком точный текст ошибки), судьба заброшенных
  неподтверждённых регистраций, блокировка входа для неподтверждённых.
- **Политика удаления/деактивации пользователя** Физически
  удалить строку `users` нельзя: на неё ссылаются `contributions`,
  `goals.creator_id`, `group_members`, и это сломает историю ledger'а.
  Значит, нужен какой-то вид мягкого удаления, но конкретный механизм
  (поле, поведение при попытке снова использовать email и т.д.) - не
  продуман, вернуться отдельно.

## 3.  уточнить 

- **Как генерируется `uuid`** - на стороне Go перед вставкой, или через
  `default: gen_random_uuid()` в самой Postgres (требует расширения
  `pgcrypto`). 
- нужен ли нам ENUM или достаточно varchar + CHECK ... IN (...)
- **Поведение внешних ключей при удалении родителя** (`ON DELETE
  RESTRICT/CASCADE/SET NULL`) 
- **Актуализация `updated_at`** - `default: now()` в DBML сработает только
  при `INSERT`. Чтобы поле обновлялось при каждом `UPDATE`, нужен либо
  явный код в каждом апдейте (риск забыть в одном месте), либо триггер в БД
  (надёжнее, не зависит от дисциплины в коде).
- **Хэш пароля** - рабочее предположение `argon2id`, но не финализировано
  окончательно

## 4. Текущий срез регистрации - что именно упрощено

- Регистрация - только email + пароль (дважды, для проверки опечатки).
  Проверка совпадения двух введённых паролей - целиком на уровне валидации
  запроса в Go
- `email_verified_at` заведено на будущее, подтверждения почты пока нет как механизма.
- вход разрешён сразу после регистрации, без
  ожидания подтверждения. Когда появится подтверждение по коду - не забыть
  добавить проверку `email_verified_at` в логику входа 

## 5. Соглашения по именованию 

- Первичные ключи - `<таблица_в_единственном_числе>_id`
  (`user_id`, `group_id`, `goal_id`, `contribution_id`…), внешние ключи
  называются так же, как колонка, на которую они ссылаются.
